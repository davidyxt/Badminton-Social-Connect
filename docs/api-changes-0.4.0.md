# API changes in 0.4.0 (Player BE-2: results and rankings)

What changed in the two generated Player/PostgREST API specs between 0.3.0 and 0.4.0. These describe `/rest/v1`, not the Admin Edge adapter. Upstream admin deletion/rebuild permissions are intentionally blocked by the Final v6 adapter; see [admin-api.md](admin-api.md).

- [badminton-social-connect-api_implemented-playerBE1.yaml](badminton-social-connect-api_implemented-playerBE1.yaml): only what is built. 123 operations before, 136 now.
- [badminton-social-connect-api_v1.2.yaml](badminton-social-connect-api_v1.2.yaml): everything, including the design's Planned endpoints. 140 operations before (17 Planned), 148 now (12 Planned).

The new backend covers recording a result, confirming or disputing it,
ratings, the Rankings screen and match quick messages. How to use it, with
response shapes, is in
[features/M2-results-and-rankings.md](features/M2-results-and-rankings.md).

The short version for the frontend:

1. **New:** 10 functions and 4 tables (section 1).
2. **Changed, and your code needs to change:** writing match, result and
   dispute rows directly, plus a few response keys (section 2).
3. **Unchanged:** 96 of the 123 existing operations are the same apart from
   their example data (section 3).

Both specs are generated by `supabase/scripts/build_openapi.py` from a local
stack after `npx supabase db reset`. Don't edit them by hand.

## 1. What's new

### Functions (`supabase.rpc(...)`)

| Function | Tag | For | Returns |
|---|---|---|---|
| `submit_result({ p_post_id, p_opponent_ids, p_partner_id, p_games })` | Results | Record Result | `RecordedResult`: `{ matchId, resultId, status: 'pending' }` |
| `confirm_result({ p_result_id })` | Results | Confirm button | `MatchDetails` (same as `get_match`) |
| `raise_dispute({ p_result_id, p_reason })` | Results | Dispute button | `MatchDetails` |
| `get_match({ p_match_id })` | Results | Match Details, Result Submitted, Result Confirmed | `MatchDetails` |
| `get_my_pending_results()` | Results | Results waiting on me, and mine waiting on others | `PendingResults`: `{ toConfirm: [MatchDetails], waiting: [MatchDetails] }` |
| `get_match_messages({ p_match_id, p_limit })` | Results | Quick message history | `[MatchMessageItem]` |
| `get_rating_summary({ p_player_id })` | Rankings | Rating card on Rankings | `RatingSummary` |
| `get_rating_trend({ p_player_id, p_days })` | Rankings | 30-day trend chart | `RatingTrend`: `{ days, points: [{ date, rating }] }` |
| `get_leaderboard({ p_scope, p_state, p_limit, p_offset })` | Rankings | State and Nearby tabs | `Leaderboard` |
| `admin_rebuild_ratings()` | Admin | Ops: replay all ratings now | integer (results rated) |

Every function lists its errors in the spec, with the exact `message` to show.
A few contain `%` where the server fills in a number, for example
"Game % (% to %) is not a legal score".

### Tables (`supabase.from(...)`)

| Table | Operations | For |
|---|---|---|
| `match_message` | GET, POST | Send a quick message: `insert({ match_id, sender_id, template_code })`. Players in the match only, preset codes only, 20 per 10 minutes |
| `match_message_template` | GET | The quick message buttons: `template_code`, `label`, `sort_order` |
| `rating_history` | GET | Your own rating before and after each rated match (admins see all) |
| `result_flag` | GET | Admins only: results flagged for review |

### Schemas

New in both files: `MatchDetails`, `RecordedResult`, `PendingResults`,
`MatchMessageItem`, `RatingSummary`, `RatingTrend`, `Leaderboard`,
`MatchMessageTemplate`, `MatchMessageWrite`, `RatingHistory`, `ResultFlag`.
The implemented spec also gains `MatchMessage`. The full spec already had it
from the design; it now holds the built version.

### Realtime

New channel `match:{matchId}:messages`, built, private (pass
`{ config: { private: true } }`), event `message`. Only the match's players can
join.

### Tags

New tags: **Results** and **Rankings**. The descriptions of
"Results (tables)" and "Rankings and leagues (tables)" no longer say "not built".

### In the full spec only

These five Planned entries are now built, so they lost their
`[Planned]` label and `x-status: planned`:

- `POST /rpc/submit_result`
- `POST /rpc/confirm_result`
- `POST /rpc/raise_dispute`
- `GET /match_message`
- `POST /match_message`

**Their parameters differ from the design**, so don't code against old
copies of the spec:

| Endpoint | Design (0.3.0, Planned) | Built (0.4.0) |
|---|---|---|
| `submit_result` | `{ matchId, score }` for an existing match | `{ p_post_id, p_opponent_ids, p_partner_id, p_games }`: the game, the opponents, an optional partner and the games as `[[yours, theirs], ...]`. It creates the match itself |
| `confirm_result` | `{ matchId }` | `{ p_result_id }` |
| `raise_dispute` | `{ matchId, reason }` | `{ p_result_id, p_reason }` |
| `match_message` | `MatchMessageCreate`: camelCase `messageId`, `matchId`, `templateCode` | The table's own columns: `match_id`, `sender_id`, `template_code` (`MatchMessageWrite`). `MatchMessageCreate` is gone |

The 12 Planned entries still there are the admin moderation functions, Mini
Leagues, `resolve_dispute` and `activity_log`.

## 2. Existing endpoints: what changed

### Writes that no longer work for players

Players can no longer write matches, results or disputes directly. Use the
functions instead.

| Endpoint | Before | Now | Use instead |
|---|---|---|---|
| `POST /match_result` | Players inserted a `pending` result | **Removed** | `submit_result` |
| `POST /dispute` | Players inserted an `open` dispute | **Removed** | `raise_dispute` |
| `POST`, `PATCH`, `DELETE /match` | Anyone on the game's roster | Admins only | `submit_result` creates the match |
| `POST`, `PATCH`, `DELETE /match_participant` | Yourself, or the match's creator | Admins only | `submit_result` adds the players |
| `PATCH`, `DELETE /match_result` | Admins | Admins (unchanged), now documented | `confirm_result` for players |
| `PATCH`, `DELETE /dispute` | Admins | Admins (unchanged) | Resolving disputes is for the admin lane |

The `GET` on all four tables still works as before. Their descriptions now say
how rows are created.

**Update needed:** remove any direct `insert` into `match`,
`match_participant`, `match_result` or `dispute`. The test scripts
`supabase/tests/rls_test.sh` and `api_test.py` still do this and will fail.

### Table columns

| Table | Change | Update needed? |
|---|---|---|
| `match_result` | New columns `games` (side a points first, e.g. `[[21,15],[19,21],[21,16]]`), `confirmed_by`, `confirmed_at`. New `status` value `expired` | Only if you read the table directly: handle `expired`, and prefer `games` over parsing `score` |
| `dispute` | New column `result_id` | No |
| `notification` | New `type` values `result_confirmed`, `result_expired` | Yes, if you map types to icons (see below) |

### Function responses

| Function | Change | Update needed? |
|---|---|---|
| `get_game_details` | `matches[]` now lists your matches in the game, each a full `MatchDetails` (was always `[]`). New `canRecordResult` | Yes: show matches and the Record Result button |
| `get_player_history` | Each match has `ratingChange` (integer, null for doubles and until the nightly run) and `verificationStatus`. `gameId` and `location` can be null (a match not tied to a game; only in the dev seed) | Optional: show the change and the badge; allow null `gameId` |
| `get_my_home`, `get_my_profile`, `update_my_profile` | `ratingCard` now has real values for `grade`, `status`, `stateRank` and `ratingChangeThisMonth` (an integer now, always null before). New keys `placement` (`{ played, required, opponents, opponentsRequired }`) and `ratingsUpdatedAt` | Yes, if the card hid these keys: show the grade, or "Placement in progress, n of 10" from `placement` |
| `get_player_profile` | New key `grade` (null while provisional). `rating` is now the real rating (null before the first rated match) | Optional: show the grade |
| `admin_game_post_deletion_impact` | `rating_changes` is now a list of `{ player_id, username, points_from_this_game }` (was always null) | Yes, for the admin delete warning |
| `get_notifications` | Same shape, but the new types `result_confirmed` and `result_expired` can appear | Yes: map both to the result icon; a tap opens Match Details (`matchId`) |

### Behaviour without a spec change

- **Ratings change overnight**, not when a result is confirmed. Screens that
  show a rating should show "Updated <date>" from `ratingsUpdatedAt`. The
  Result Confirmed screen should say "Your rating updates overnight" while
  `result.ratingPending` is true.
- **`ranking` table** (`GET /ranking`): same columns, but the singles row is
  now written by the nightly rating run, not by the seed.

## 3. Existing endpoints that need no update

These 96 operations have the same request, response and description as in
0.3.0. Seven of them have new example values only, because the dev seed's
dates move with the day the spec is built and the seed now has more players:
`get_my_games`, `search_games`, `search_venues`, `search_players`,
`get_join_requests`, `get_blocked_players`, `get_notifications`.

|---|---|
| Registration | `is_username_available`, `register_player`, `delete_my_account` |
| Profile | `set_my_profile_picture`, `remove_my_profile_picture` |
| Games and joining | `get_game_form_options`, `search_games`, `search_venues`, `get_my_games`, `request_to_join`, `withdraw_request`, `get_join_requests`, `accept_request`, `decline_request`, `invite_player`, `accept_invite`, `decline_invite`, `cancel_game_post`, `delete_game_post` |

## 4. How the spec itself changed

These changes are in the generator (`supabase/scripts/build_openapi.py`) and
the dev seed, not the API:

- Version 0.3.0 to 0.4.0.
- The script registers the new functions, with sample calls as the dev seed
  accounts.
- `submit_result` changes data, so the script never calls it. Its response
  schema and example are written into the script.
- The match lists in `get_my_pending_results` and `get_game_details` point at
  `MatchDetails`, so the match shape is defined once.
- `blockRelation` (leaderboard rows) is typed as `blocked_by_me`,
  `blocked_me` or null.
- `search_players` `location` is marked nullable explicitly, because no
  current seed player has an empty suburb.
- The dev seed gained:
  - a pending result waiting for Alice (game `c108`, Bob v Alice)
  - three quick messages on match `d101`
  - an unrated sample (Ivy) for `get_player_profile`

  These give real examples for the pending, message and unrated cases.
- Table operations follow the database grants. `INSERT` on `match_result` and
  `dispute` was revoked, because no access rule allowed it, so those two
  `POST` operations no longer appear.
